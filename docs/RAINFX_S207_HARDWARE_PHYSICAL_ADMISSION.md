## Explicit consumer binding

The standalone s206 executable-bound receipt is not silently reused by a different
program. A new version-2 binding is issued after rechecking the saved two-pose
CPU qualification and four exact cache rebuilds. It binds:

- The current full physical consumer executable.
- Complete schedule, frame-window stream, cache/refresh programs, both qualified
  metric payloads and complete bootstrap proof files.
- Both qualification records, their sealed delivery and the qualification
  consumer executable.
- Original cache/physical/adaptive shader binaries and the explicit shader
  candidates described below.
- Adapter index, vendor/device, LUID and driver version.

The native reader checks all listed file hashes, required input identities,
qualification-record presence and actual shader coverage before cache producer
draws. A missing/mismatched consumer or file hash is refused before device
construction. Adapter/driver mismatch is refused after device construction but
before producer draws; construction can allocate/upload inputs. File hashes bind
provenance and do not replace full-byte GPU comparisons. The initial bootstrap
checks every byte of all ten qualified proof images. Subsequent cache generations
retain the old-header/metric preservation and complete expected-header/metric
predicates from s204.

The binding concerns immutable files and this private immediate-context stream.
It is not a signature, an external-writer protocol, a general GPU completion
proof or a CSP lease. Current device selection remains adapter 0; this stage does
not establish which enumerated adapter the game uses.

## Hardware source gate failure and correction

The first unmodified physical attempt passed qualified bootstrap but refused
source admission in frame 0. No bank or solver time was published; three accepted
intervals remained as debt. The code had previously printed unconditional water/
clock-success booleans even in that case. The new consumer reports those booleans
from actual published commits. The preliminary outputs are retained separately
and excluded from final success evidence.

A read-only failure snapshot located exactly 40 source-slot rejections. Every
rejected slot was a mismatch between two independently recomputed copies of the
same previous head packet. Volume bits matched; momentum differed in low bits.
The exact provenance predicate correctly rejected the disagreement.

Two narrowly scoped shader candidate changes address this class of issue:

1. Explicit `precise` products and sums in the shared world-vector, UV-velocity
   and volume-to-momentum helpers fix the operation order in the duplicate packet
   producers. This prevents independent compiler fusion/reassociation choices
   from defining different packet bits for the same operations. Eight inherited
   shader variants contain this helper change.
2. A zero pool debit preserves the complete old packet and emits a zero debit
   directly. It no longer computes an unnecessary `old.r / old.r`, multiplies
   momentum and subtracts it again. Positive requested debit retains the original
   arithmetic and admission conditions. Three source-cell shader variants contain
   this exact no-op identity. The 40 observed slot failures above establish the
   duplicate-packet issue; this stage does not claim an isolated ablation proving
   the zero-debit branch was a separate cause of that first refusal.

The candidate binaries are stored only in this stage's evidence folder. Native
shader keys explicitly resolve to these 11 candidates through a compiled map,
and the version-2 binding covers both old and candidate binaries. No prior shader,
program/uniform stream, schedule, asset or game file is overwritten. Finite,
nonnegative, exact ownership, debit, conservation and tolerance predicates remain
in place. No equality test is changed into a tolerance to force admission.

The corrected hardware run completes 1,051 adaptive attempts: 1,043 accepted
substeps and eight recovered refusals. The prior WARP fixture had 1,049 attempts,
1,042 accepted and seven refusals. Backend/rounding-sensitive adaptive decisions
can differ; exact tick consumption and conservation are checked independently.
Hardware shadow/reuse state parity passes. Cross-backend WARP bit parity is not
claimed, and numerical sensitivity remains part of physical accuracy review.

## Performance scope and next implementation

Capture policy is `controls`: optional large archive captures remain disabled,
while decision, adaptive, cache, stock and final-bank validation stay enabled.
The inherited timestamp observer and CPU read/wait counters are recorded, but
uploads, allocation and adaptive bounds/carry are not yet completely categorized.
These are single sequential debug observations with mandatory validation and
text traces, not a statistically reliable speedup or FPS measurement. The
simulation spans 4.32 seconds even though native execution takes much longer;
it is not a long-duration stability result.

Next complete measurement coverage without changing solver semantics or adding
completion waits. Separate shader execution, uploads/copies, CPU readback,
allocation and existing polling/sleep cost. Compare repeated ordered hardware
runs only after the instrumentation preserves these state/ledger/time/stop gates.
Use those measurements to choose a concrete production optimization.

Independent full physical/time accuracy, complete CPU/startup streaming, long
duration, common optics, CSP scheduling/completion and live adoption remain open.

are preserved. No user game test, commit or push is required here.

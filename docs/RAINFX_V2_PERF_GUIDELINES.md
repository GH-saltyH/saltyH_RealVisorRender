# RealVisor / RainFX2 성능 평가 지침 (PERF-1–14에서 얻은 규칙, 2026-11-06)

새 기능, 셰이더 패스, 텍스처, 콜백을 추가할 때는 구현 전후로 아래를 거친다. 근거 사례는 `RAINFX_V2_PERF_RESEARCH.md`에 있다.

## 1. 설계 단계 (구현 전)
1. **비용이 무엇에 비례하는지 적는다.**
   - 화면 픽셀 × 후보 수, 셀 수, 방울 수, 패스 수 중 무엇인지 쓴다.
   - 픽셀 × 후보 구조는 '픽셀 무관 계산'을 반드시 분리한다(PERF-3 predict, PERF-9 rec). 같은 값을 여러 픽셀 / 텍셀이 다시 계산하면 안 된다.
2. **후보 루프는 증명된 범위만 돈다.**
   - 커널 / 효과의 지지 반경을 해석적으로 유도한다(PERF-7 r2SupportCore). 셀 단위 마스크로 닿지 않는 후보를 미리 걸러 낸다(PERF-10).
   - 휴리스틱 반경(×3.5 같은 여유)은 쓰지 않는다. 쓴다면 왜 상한인지 증명과 수치 검사를 남긴다(check_tight_support.py 방식).
3. **소비자가 없으면 생산하지 않는다(PERF-8).**
   - 캡처, 복사, bake 같은 생산 작업에는 소비자 목록을 적는다.
   - 소비자가 그리지 않는 조건(Visible, 설정)과 똑같은 조건에서 생산도 건너뛴다. 조건은 소비자 코드의 조기 return과 같은 식이어야 한다.
4. **매 프레임 CPU 작업을 금지한다(PERF-14).**
   - 디스크 IO, 큰 문자열 생성(키 / 로그), 클로저 / 테이블 / vec 할당을 매 프레임 하지 않는다. 캐시 + 변경 감지 또는 시간 제한을 쓴다.
   - 디버그 / 표시용 데이터(labels 등)는 필요한 프레임에만 만든다.
5. **패스 수가 곧 CPU 비용이다(PERF-11 / 12).**
   - CSP의 updateWithShader / render.mesh는 호출당 고정 CPU가 든다(프로파일러 on 기준 약 0.03–0.05 ms). 값 개수와는 무관하다.
   - 새 패스를 만들기 전에 기존 패스에 합칠 수 있는지 먼저 본다(입출력 의존이 같으면).

## 2. 공유 리소스 / 충돌 검증 (구현 중, 필수)
1. **텍스처 레지스터 예산.**
   - ui.fx(scene include)는 user t0–t13(t14 shadow array)까지이고, mesh.fx는 t0–t12(t13+ 예약)까지이다.
   - 공유 시뮬레이션 표는 14 / 14로 가득 찼다 → 새 입력은 그 패스 전용 표를 쓴다(rec, msk 방식).
   - check_rainfx2_shaders.py가 init.lua 표를 직접 읽어 검사한다. 새 패스는 PASSES에 등록한다.
2. **값(gR2*) 출처를 하나로 둔다.**
   - 여러 패스가 같은 계산을 공유하면 값도 한 함수에서 만든다(candValues).
   - 셰이더가 읽는데 Lua가 설정하지 않은 값은 게임에서 컴파일 오류 없이 0이 된다 → VALUE_SOURCES 검사에 등록한다.
3. **같은 데이터를 쓰는지 확인한다.** 사전계산 결과는 그것을 만든 입력 텍스처의 식별자를 기억한다. 소비 시점의 바인딩과 다르면 원래 경로로 돌아간다(recS / recLM).
4. **순서 의존.**
   - 캡처나 복사의 위치를 옮기면 그 뒤의 모든 소비자를 다시 확인한다. PERF-4b에서 캡처 순서 역전으로 E2 / E3이 사라졌다.
   - 렌더 콜백 안에서는 dispose / 생성 같은 수명 전환을 하지 않는다(script.update에서 한다).
5. **수명.** 새 캔버스는 dispose 목록에 넣고, 캐시된 params / 유효 플래그도 함께 초기화한다(LIFE-1: 해제된 메쉬 재사용 사례).
6. **하나의 호출 지점.** visor의 r2AddDrop은 호출 지점을 하나로 유지한다(FXC가 두 번째 지점에서 조용히 실패했다).

## 3. 검증 (구현 후, 필수)
1. **이미지 동일성을 주장하는 최적화에는 verify 모드를 넣는다.** 건너뛴 작업이 실제로 기여했으면 빨간색으로 표시한다(gR2TightReach 2). 사용자가 Heavy Rain과 Light Drizzle에서 2분 이상 주행해 위반 0을 확인한다.
2. **측정 방법을 고정한다.**
   - GPU: Render Stats 항목(`RainFX2 sim/<pass>`, `RainFX2 draw`, `…/depth`, `RealVisor/Glass/*`)을 본다.
   - CPU: RainFX 탭 프로파일 표(`RV <구간> (CPU)`)를 본다.
   - FPS: Render Stats 팝업을 열지 않은 새 세션에서 같은 지점 / 날씨로 잰다. 팝업은 FPS를 떨어뜨리고, 닫아도 복원되지 않는다.
3. **A/B 토글을 둔다.** 새 경로에는 끄는 토글을 두고, on / off 측정으로 효과를 확인한다.
4. **효과가 없으면 제거한다.** 측정 차이가 변동 범위 안이면 코드를 남기지 않는다(occ PERF-4, lean values PERF-12).
5. **FXC 경고를 0으로 유지한다.** 정수 나눗셈은 uint로, 초기화되지 않은 변수는 단일 출구로 처리한다.

## 4. 비용 예산 (Heavy Rain 정지, 2026-11-06 기준)

| 항목 | GPU (ms) | CPU (ms) |
|---|---|---|
| RainFX2 sim | 0.58 | 0.64 |
| visor colour | 0.57 | 0.08 |
| visor depth | 0.37 | 0.06 |
| rec + msk | 0.06 | 0.02 |
| glass 스택(E1–E7) | ≈ 1 | 0.43 |

- 새 기능은 '예상 GPU / CPU 증가량'을 설계 문서에 적고, 측정 후 실제 값과 비교한다.
- 한 기능이 0.2 ms를 넘으면 사용자에게 먼저 비용과 대안을 제시한다.

# RainFX s84 — P4a 게임 검토와 같은 프레임 진단

Date: 2026-10-15. Status: ACTIVE — 제공된 물 원장 통과, FPS는 사용자 관찰상 동등. 큰 Courant로 수송 시간 정확도 gate 미통과. 수동 진단 보강 완료.

## 1. 기준과 측정 조건

s83 P4a를 동일 리플레이 세션에서 검증한 사용자 결과다. 날씨는 이전과 같고,
리플레이 로드 후30분 이상 지난 뒤 세션을 유지하며 관찰했다. 초기 로드 변동을
줄인 통제는 유효하지만 **P4 자체를30분간 구동했다는 뜻은 아니다**.

이번 s84는 결과 분석과 수동 진단만 수정했다. P4의 물리 수송·광학·source·계수,
기존 튜닝/표시 크기와 기본 OFF 정책을 유지한다. 사용자 커밋은 하지 않는다.
브랜치는 `codex/rainfx-physics-weather`, HEAD는 사용자 P2 stamp1ad4a95다.

원본: `diagnostics/2026-10-15/s84/p4_actual.log`.
재계산: `tools/review_s84_p4_game.py`, 보고서 `s84/game_checks.json`.

## 2. 원장 — 제공된 조건에서 통과

각0초의 과거 혼합 interval은 제외했다. 아래는 **제공된 스냅샷끼리** 차분한 값이다.

| 조건/구간 | published 경과/s | 유입/mm³ | residual 증가/mm³ | 유입 대비 절대 오차/% |
|---|---:|---:|---:|---:|
| 정차0→15 | 14.991760 | 413.482422 | .006522 | .00157733 |
| 정차15→30 | 14.961519 | 293.579102 | .008145 | .00277438 |
| 137km/h0→15 | 15.578989 | 2090.406250 | .001639 | .00007841 |
| 137km/h15→30 | 14.757396 | 1944.666015 | .009588 | .00049304 |

최대 상대 구간 오차 `2.77438e-5`는 s73 기준 `1e-4` 아래다.
최대 누적 residual은.079355mm³, 최대 누적 상대 오차 `3.12425e-6`이다.
원장의 양수 오차가 서서히 늘어나는 장시간 float32 문제는 여전히 남는다.
Courant 제한은 실제 전달량을 줄이지만 줄인 양을 donor에 남기므로 물 손실과는 다르다.

### 출력 interval이 제공된15초 간격과 다른 이유

예를 들어 직진15초 로그의 `intervalSeconds=.158994`는 제공된 직전 스냅샷과의
15.578989초가 아니다. 직진30초의 `.186126`, 정차30초의14.791594도 다르다.
버튼의 `previousLog`는 매 성공 readback마다 갱신되므로, 중간 클릭 로그가 생략된
자료에서는 출력 interval/rate/residualDelta를 그대로15초 구간 값으로 쓰면 안 된다.
현재 자료는 누적 counter와 published clock으로 재계산했다. 이 차이를 물리 dt
손실이나 로그 원장 오류로 판정하지 않는다.

## 3. Courant — 시간 정확도 gate 미통과

| 조건 | max C | 제한 셀/젖은 셀 | 제한 셀 비율/% | 제한 셀 film/mm³ |
|---|---:|---:|---:|---:|
| 정차0 | 6673.315 | 1651/117822 | 1.40127 | 343.043 |
| 정차15 | 5450.913 | 818/117748 | .69470 | 502.572 |
| 정차30 | 97620.234 | 737/117705 | .62614 | 600.454 |
| 직진0 | 567.788 | 876/117611 | .74483 | 73.522 |
| 직진15 | 7371.622 | 1265/117910 | 1.07285 | 509.148 |
| 직진30 | 70874.547 | 1178/118100 | .99746 | 985.830 |

셀 개수의 비율만으로 제한이 경미하다고 볼 수 없다. 제한 셀에 최대 약.986mL가 있다.
그러나 물 원장과 flow 로그의 프레임은48–81프레임 차이가 있다. 따라서 위 제한
물량을 근처 원장의 film으로 나눈 값을 **정확한 같은 프레임의 질량 비율**로 발표하지 않는다.

현재 limiter의 속도 배율은 `min(1,.8/C)`다. 최대 지점에서는 약1/122025로 줄어든다.
이는 음수 재고를 막는 안정장치이며, 현실 시간의 흐름 속도가 맞는다는 의미는 아니다.
동일한 초기 속도를 고정해 균등 substep을 잡으면 최악 약122026회가 필요하다는
크기 추정이다. 비선형 field의 실제 적응 step 횟수를 측정한 값은 아니다.
단순히 전역 substep 몇 회를 추가해 이번 최대값을 해결했다고 할 수 없다.

## 4. 원인 조사에서 확인한 것과 남은 것

코드의 단위 경로:

```text
h_m = (film_mm3 / supportedArea_mm2) * .001
v_m_s = rho*h_m^2/(3*mu)*a_tangent + h_m/(2*mu)*tau
uvTravel = inverseWorldJacobian(v_m_s) * sim.dt
C = L1(uvTravel * grid)
```

면적 DDS는 현재 geometry와 SHA가 맞고, 총40288.60096mm²다.
지원 셀123224개의 면적 min/median/max는.0192231/.3357066/.8038341mm²다.
즉 supported 면적0을 나눈 경우라는 근거는 없다. 코드의 mm→m 변환과 실제
world Jacobian 경로에서도 별도1000배 단위 오류를 발견하지 않았다.

실제 메쉬와 production `ffEvaluate`를 사용한 WARP 시험:
identity world transform, 중력만, dt1/60초, **균일한 가상 film**을 놓았다.

| 가상 두께 | max C | median C | C>.8인 지원 셀/% |
|---|---:|---:|---:|
| 100µm | 5.38258 | .78868 | 49.0051 |
| 1000µm | 538.258 | 78.8682 | 100.0000 |

이것은 사용자의 실제 분포/자세를 복원한 결과가 아니다. 정상 SI 단위에서도
현재 준정상 `h²` 속도와 미세 격자만으로 큰 C가 생긴다는 검증이다.
게임의 최대97620이 어느 두께/셀 크기/힘에서 나온 것인지는 기존4-float 로그로
정확히 분해할 수 없다. 국소 고임, partial 면적과 유입 집중, 압력·운동량 부재에
따른 모델 범위 초과 등이 후보이며 어느 하나로 확정하지 않았다.

### 대안과 비용 판단

| 대안 | 비용/효과 판단 |
|---|---|
| 수동으로 두께·셀 크기·제한 질량·속도 비율 분해 | steady 비용 변화 없음. 이번에 구현해 우선 원인을 분리한다. |
| 2–8회 bounded substep | 보통 크기의 C에는 도움. flux/commit 반복과 원자 게시용 scratch가 필요하고, 큰 최대값과 준정상 모델의 범위 문제는 별도로 남는다. 실제 ms gate 필요. |
| 더 거친 물리 grid | 일반적인 C와 픽셀 작업량 감소. 두께 분포와 trail 공간 해상도 손실이 있고, 수만 단위 C를 해소하는 비율의 축소는 부적절하다. |
| 국소 고임을 포함한 압력/운동량 또는 보존적 head 재분류 | 실제 상태에 맞는 다음 모델 후보. 추가 재고/paired transfer·안정성·pass 비용을 설계/검증해야 한다. 현재 저비용 확정은 아니다. |

표시 gain은 위 식에 접근하지 않는다. 물리 h/질량을 임의로 줄여 이 수치를
맞추는 변경은 하지 않았다. 현재 목표는 큰 C를 숨기는 것이 아니라 모델/시간해상도의
책임 구간을 분리한 뒤 적절한 다음 수송 모델을 선택하는 것이다.

## 5. 화면과 영상 검토

`images/s83_P4/`의6개 µm 이미지 전부를 확인했다. 정차에서 넓은 고임 패턴이
대체로 유지되고 주행에서는 높은 색상 구역이 넓어지는 모습이다.
파일은 사용자 메시지의 **P3Only 항목**에 있으므로 P3-only 자료로 취급했다.
파일명의 P4는 이번 검증 단계 이름이며, 개별 이미지에서 P4 활성 여부는 UI가
닫혀 있어 재확인할 수 없다. 이를 P4 film µm 결과로 단정하지 않는다.
이 view는1000µm 이상에서 색상이 포화되고 배경과 alpha 합성하므로 실제 최대
물리 두께를 스크린샷 색상에서 읽을 수 없다.

실제 확인한 영상 표본:

- `_P4Test_P3Only_Idle_137kmh_Inspect.mp4`:75.566667초,8개 시각 표본.
- `_P4Test_P3P4Log_137kmh.mp4`:49.733333초,8개 시각 표본.
- `_P4Test_P3P4Log_Idle.mp4`:36.833333초,8개 시각 표본.

메타데이터/시각은 `s84/media.json`, contact sheet는 `s84/frames/`에 있다.
P4 주행의 약27.63초 visor 원해상도 crop과 정차 약28.65초 UI crop도 확인했다.
P4 정상 광학에서 국소 왜곡과 머리 쪽 경계 굴절이 보이고, UI는 P4 제어·ready=true를 표시한다.
표본 전체에서 전체 FX 레이어 소실은 보이지 않았다. 각 영상을 연속 재생해 모든
프레임의 미세 떨림/head–trail 연결을 인증한 검증은 아니다.
E2/E3 등 기존 유리 광학도 장면에 포함되므로 모든 배경 왜곡을 P4에 귀속하지 않는다.
현재 runoff는 source kernel 거부와 transport 유출을 합친 누계여서
기존 로그만으로 P4만의 배수량을 따로 분리할 수도 없다.

## 6. 성능과 메모리 판정

P3-only FPS는 정차65/66/66, 직진65/70/65이며 사용자는 P3/P4를 구간별로
동일하다고 평가했다. **제공된60% 조건에서 관찰 가능한 FPS 악화가 없다는
결과를 수용**한다. 별도의 P4 수치 벡터나 GPU timestamp 차이는 제공되지 않았으므로
정확한0ms 추가 비용 또는100%/4096 전체 부하 통과로 환산하지 않는다.

메모리는 P3-only 정차의79.70–145.92MB 한 구간이다. 이번 P4 별도 최소/최대는 없다.
워밍업 통제는 반영하지만 이 범위로 P4의 장시간 메모리 증가량을 계산하지 않는다.
앞선 s82의3분/40회 토글 누적 없음 판정은 유지한다.

## 7. 이번 진단 변경

**steady 수송 shader·resolve·source·optics와 물리 prepare/publish는 변경하지 않았다.**
수동 `Log P4 transport limiter`만16-float로 확장했다.

- 기존 max C/제한 셀/젖은 셀/제한 film;
- 같은 프레임 totalFilmMM3, limitedMassShare;
- `massWeightedVelocityRetained`: 각 film 체적으로 가중한 `min(1,.8/C)` 평균.
  남은 물의 비율이 아닌 **모델 속도의 보존 비율 추정**이다;
- uncapped maxFilmUM 및1mm 초과 셀의 film 재고;
- 최대 C의 셀 좌표, 그 셀의 film µm·면적·최소 metric stride/µm·접선 가속도/m/s².
  좌표에서 static cells의 coverage/coating도 후속 분석할 수 있다.

극값의 위치/두께/면적 record는 같은 max C를 따라 함께 reduce한다.
total/weighted 합에는 보상 합산을 사용한다. 표시 texture의60000µm cap을 읽지 않고
실제 재고/면적에서 두께를 계산한다.

`Log P3 actual water budget` 버튼은 이제 같은 호출에서 두 수동 요청을 한다.
두 readback이 모두 준비되면 **같은 frame 번호**의 원장과 P4 진단이 출력된다.
이미 readback 진행 중이면 새 쌍을 제출하지 않는다. 최초 shader 준비 중에는
한쪽만 출력될 수 있으므로 잠시 뒤 한 번 다시 누른다.
기존 별도 P4 버튼도 유지한다.

진단 canvas 개수는3개 그대로, payload는19184→76736bytes로 증가했다.
차이는 **버튼을 누른 뒤 약56.2KiB**이며 steady pass/캔버스/프레임 readback 추가는 없다.
실제 게임에서 물리 문제가 해결됐다고 기록하거나 P4 gate를 완료하지 않았다.

검증: `tools/check_s84_flow_diagnostics.py`.
FXC /Ges /WX WARP에서16-float/MAX·SUM/argmax·물리 단위, 실제 메쉬 두께 probe,
실제 Lua의 같은 프레임 두 요청·busy gate·stale/reset/40회 토글을 확인했다.
기존 s83 regression 도구의 수동 readback shape/mock도 현재16-float ABI에 맞췄다.

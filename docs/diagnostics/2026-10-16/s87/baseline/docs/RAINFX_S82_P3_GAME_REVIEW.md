# RainFX s82 — P3 실제 게임 원장·표현·비용 검토

Date: 2026-10-15. Status: REFERENCE — 제공된60% 원장 및3분/40회 토글 메모리 누적 관찰 gate 통과. P4a 수송은 s83에서 진행; 전체 품질·장시간 정밀도·10분/100% 비용 gate는 계속.

## 1. 기준과 사용자 결과

사용자 P2 스탬프 `1ad4a95f48d7b683f38b9134bf6c202eb363780e` 이후의
**s81 전달 소스 그대로** 검토했다. 브랜치 `codex/rainfx-physics-weather`.
이번 s82는 로그·미디어 검토와 원인별 진단이며 runtime, shader, 물리 계수와
표시 크기 gain은 변경하지 않았다. 커밋/push는 사용자가 한다.

사용자 조건: 이전과 같은 날씨/시간, 낮 약60% 강수. 트랙 위치는 다르다.
정차 및137km/h 직진 각0/15/30초 원장6개를 제공했다.
P2=66FPS, P3=65FPS이며 사용자 측정 오차가 약1FPS다.
두 모드에서 GC 전 Memory가 처음142MB, 나중165MB였다.
**GC 후 최저값이나 통제된 토글 반복 시계열은 없다.**

원본과 계산:

- `diagnostics/2026-10-15/s82/p3_actual.log`
- `diagnostics/2026-10-15/s82/game_checks.json`
- 재계산: `tools/review_s82_p3_game.py` (`--media`로 영상 샘플도 추출).

## 2. 실제 물 원장

```text
residual = input - (film + micro + drops + bounce + exit
                    + headEvap + fieldEvap + runoff)
```

`trailTransferred`는 head→field 내부 전달량이다. 손실로 다시 빼지 않는다.
capacity 물도 이미 field에 포함되어 있어 추가로 빼지 않는다.
각0초 로그의 interval에는 이전 혼합 구간이 들어가므로 다음 표에서는 제외했다.

| 안정 구간 | 실제 경과/s | 유입/mm³ | 오차 증가/mm³ | 유입 대비 절대 오차/% |
|---|---:|---:|---:|---:|
| 정차0→15초 | 15.126295 | 128.152343 | .002618 | .00204288 |
| 정차15→30초 | 14.594769 | 140.911133 | .001500 | .00106450 |
| 직진0→15초 | 16.070831 | 1531.060547 | .007496 | .00048960 |
| 직진15→30초 | 14.456831 | 1695.226563 | .008228 | .00048536 |

최대 구간 상대 오차 `2.04288e-5`는 s73의 사건 원장 기준 `1e-4` 아래다.
누적 유입15.054–29.915mL에서 최대 누적 residual은 **.070037mm³**,
최대 상대값 `2.34116e-6`(.000234116%)이다.
**제공된 조건의 보존 gate는 통과**하지만 모든 환경/장시간 정밀도 통과는 아니다.

두30초 안정 구간의 평균:

| 조건 | 유입/mm³/s | film 순증가/mm³/s | head→trail/mm³/s |
|---|---:|---:|---:|
| 정차 | 9.052956 | 1.608872 | .912854 |
| 직진 | 105.684055 | 33.425819 | 1.800285 |

정차 공급이 이전 P2 재검증의43.918mm³/s보다 적다. 이번에는 트랙 위치가 다르고
동시 P0의 법선·상대풍 입력이 없어 이를 공급 오류로 단정하지 않는다.
직진 film 순증가는 trail 전달보다 훨씬 크다. 넓은 수막 표현의 주된 재고는
head 경로만이 아니라 입사 film/capacity 및 micro 전환에서 온다.

FPS 값은 사용자 관찰 결과로 기록하고 해당 프레임을 직접 검증했다고 쓰지 않는다.
이미지와 원장 로그의 정확한 프레임 대응도 없다.

실제 supported 면적40288.60096mm²로 원장 film을 나눈 **전체 면적 평균**은
정차86.407→87.594µm, 직진175.038→200.366µm다.
이 평균은 국소 peak나 표면 전체가 균일하게 덮였다는 뜻이 아니다.
굴절은 절대 높이만으로 켜지는 임계 효과가 아니다. 현재 shader는 높이 변화로
표면 기울기를 만들며, 균일한 높은 film에는 광학 coverage가 있어도 굴절 offset은 작다.

**장시간 흐름은 아직 구현 범위 밖이다.** 내부 field는 증발 외에 능동적으로
배수되지 않는다. 직진30초에서 film이 약1.020mL 증가한 것은 원장상 유입이
남은 결과이며, 이 고임을 완성된 rivulet/sheet 흐름으로 평가하면 안 된다.
P4 conservative transport 및 head 재흡수가 다음 물리 구현의 우선 대상이다.

## 4. 비용과 메모리

66→65FPS를 frame time으로 바꾸면15.1515→15.3846ms, 명목상 **+.2331ms**다.
약1FPS의 측정 오차 안에 있으므로 분리된 GPU 비용 또는 확정적인1FPS 회귀로
해석하지 않는다. 100% 강수/4096 활성 슬롯 및 p99 비용은 이번 자료에 없다.

s81의4096-slot 추가 raw storage는18,723,008bytes (**17.856MiB**),
수동 원장 canvas는19,296bytes다. 이는 정적 cells와 canvas payload 계산이며
Lua heap/SDK/driver 내부 캐시·allocation padding·compile 작업 메모리와 동일한 측정값이 아니다.
따라서142→165MB 증가를 이 값만으로 설명하거나 누수로 확정할 수 없다.

`check_s82_p3_precision_and_reset.py`에서 실제 Lua module과 main reset/publish를
실행하고 CSP canvas만 mock했다. P2/P3 **100회 모드 전환** 결과:

- P2 정상 상태 live bank8개, P3 정상 상태16개로 일정했다(4 main 포함).
- 매 reset 뒤 live bank0개; stale manual readback의 data도 dispose됐다.
- 기존11개 pending gate, metadata 소유권, 수동 budget 및 clock 검사도 통과했다.

이는 조사한 소유권 경로에 반복 캔버스 누적이 없다는 근거다.
**실제 SDK 캐시나 GC 후 heap plateau 검증을 대신하지 않는다.**
실제 누수 여부를 위해 P2 고정, P3 고정, P3 OFF→ON5회에서 각각 GC 직후의
최저 Memory를 요청했다. 매 프레임 강제 GC나 전체 캐시 파기는 도입하지 않았다.

## 5. 장시간 수치 정밀도 — 남은 문제

게임 residual은 .021989→.070037mm³로 양의 방향으로 늘었다.
현재 field RGBA32F에서 다음 연산은 보상 합산을 하지 않는다:

1. 작은 incoming을 기존 film/micro에 더하기;
2. micro→film 전환과 증발;
3. 누적 evaporation/runoff 채널 증가;
4. 수동16×16·coarse 합산.

P2 전역 source 원장의 Kahan 보상과 별개로 field에서 반올림이 쌓일 수 있다.
이것이 **게임 residual의 유일한 원인이라는 증명은 아직 없다**.
동시 P2 extended budget 및 field sum 비교가 있어야 책임 구간을 분리할 수 있다.

기존12초 검사는 이 위험을 충분히 다루지 못했다. 이번에는 production
`pfResolve` 연산을 가져와 직전 texture Load만 loop 인자로 바꾼 FXC /Ges /WX,
D3D11 WARP 시험을 추가했다. 셀 한 곳에 고정 소량을42007/66000번 연속 유입하는
조건에서 유입 대비 오차는 **.00131–.16034%**였다.
일부 사례는 사건 원장 기준 .01%를 넘었다.
이는 지속적으로 같은 셀을 채우는 연산 스트레스이며 실제 sparse rain 공급·전체
publish 파이프라인의 장시간 게임 재현은 아니다. 보고서는 `s82/precision_checks.json`.

정밀도 보강은 물을 residual만큼 만들어 넣거나 evaporation으로 재분류하는
보정이 아니라 실제 누적 roundoff를 보관하는 방식이어야 한다.
4채널 full-size RGBA32F compensation 두 bank라면 raw **+9.281MiB**, 최소
추가 read/write payload 약9.73MB/step가 든다. shader/API 구조에 따라 pass 비용도
늘 수 있다. 현재 게임 오차가 허용치 안이고 비용 제한이 중요한 만큼, 이 방식을
측정 없이 추가하지 않았다. P4 transport 설계에서 저장할 loss/compensation 채널과
합산 순서를 함께 평가하고, sparse 유입·건조·배수를 포함한 장시간 gate를 재검증한다.

## 6. 판정과 다음 단계

- **통과:** 제공된60% 정차/직진의 물 원장; P3 field 생성과 정상 광학 표현의 근거.
- **현 비용 관찰:** 추가 비용은 사용자 측정의 약1FPS 오차 내. 성능 전체 통과 아님.
- **메모리 후속 판정:** 아래§7의3분/40회 토글 범위에서 지속 누적이 관찰되지 않았다.
- **미확정:** 개별 head/trail 연결 품질, 10분 및100%/4096 조건의 메모리·비용,
  장시간 수치 정밀도.
- **다음 구현:** 원장·정밀도 비용을 함께 검증하며 P4 보존적 수송·배수/재흡수 진행.
  Smear 및 legacy local impact film을 다시 켜서 고임을 가리지 않는다.

이번 결과로 P3 전체 또는 물리/material calibration 전체를 완료 처리하지 않는다.
사용자 측정과 진단을 보존했고, s81 runtime SHA와 튜닝은 그대로다.

## 7. 사용자 실제 메모리 후속 측정 (2026-10-15)

같은 리플레이를 재생하고30FPS 녹화에서 Memory 최대/최소를 관찰했다.
시간 표본 간격은 약33.3ms다. 아래 두 끝값은 모두 **Memory/MB**이며 FPS가 아니다.
원본 수치/관찰은 `s82/memory_followup/measurements.json`, 계산은 `checks.json`에 있다.

| 조건 | 최소/MB | 최대/MB | 해당 기준 대비 최소 변화/MB | 최대 변화/MB |
|---|---:|---:|---:|---:|
| P2 리플레이 시작 | 66.00 | 121.00 | — | — |
| P2 3분 후 | 66.00 | 123.80 | .00 | +2.80 |
| P3 리플레이 시작 | 68.98 | 138.10 | — | — |
| P3 3분 후 | 62.13 | 114.82 | −6.85 | −23.28 |

토글 비교는 사용자가 게임 진입 후 두번째 사이클에서 관찰했다.
5회→40회에서는 최소−3.31MB, 최대−7.53MB로 내려갔다.
토글 횟수가 늘수록 회수되지 않은 물체가 계속 쌓이는 패턴을 이 수치에서 찾을 수 없다.
5회에서 오른 값만 분리해 누수라고 판정하거나40회−기준 차이를 횟수로 나누어
누수율을 추정하지 않는다.

사용자는 P3에서 리플레이 시작 직후 시간이 지날수록 최소 Memory가 내려가는
패턴을 공통으로 관찰했다. 초기 작업/캐시 수명·GC 타이밍 등의 변화와 양립하지만
각 기여를 이번 범위 값으로 특정할 수 없다. P2의 같은 시간 패턴은 관찰하지 않았다.
이 시간 편향 때문에 P2/P3 순간 범위로 모드별 고정 메모리 차이도 확정하지 않는다.

**판정:** 제공된3분 유지 및40회 토글 범위에서 지속 메모리 누적은 관찰되지 않았다.
앞선 실제 Lua 소유권100회 검사(캔버스 mock)와 함께, 현재 P3 토글 경로의
지속 누수 의심을 뒷받침하는 근거는 없다. 이 범위의 메모리 누적 관찰 gate는 통과로 기록한다.
앞선142→165MB GC 전 peak 증가만으로 누수를 의심했던 항목은 본 결과로 갱신한다.
runtime cleanup이나 강제 GC를 추가할 근거도 없어 물리/광학/메모리 코드는 유지했다.

이는 모든 상황에서 누수가 없다는 인증이 아니다. 전체 영상/원시 시계열과 반복 표본이
없으며30FPS 표본은 더 짧은 peak나 정확한 GC 직후 trough를 놓칠 수 있다.
앱 Memory는 별도 GPU/driver 자원량 측정도 아니다. 설계의10분 warm run 및
100% 강수/4096 활성 슬롯/p99 gate는 별도로 남는다. 현재 자료에 대한 반복 측정 요청은 추가하지 않는다.
